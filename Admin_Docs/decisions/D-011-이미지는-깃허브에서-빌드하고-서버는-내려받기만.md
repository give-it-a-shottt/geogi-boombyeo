# D-011 이미지는 깃허브에서 빌드하고 서버는 내려받기만 한다

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]

무엇을: 프로그램을 포장하는 일(빌드)은 깃허브가 하고, 서버는 완성된 것을 내려받아 켜기만 한다. 서버는 지금 쓰는 메모리 1GB짜리를 그대로 쓴다. (서버를 그대로 쓰는 것은 사용자 결정, 2026-11-23)
비유: 깃허브는 공장, 서버는 가게다. 가게가 좁아서 물건을 가게에서 만들지 않고 공장에서 만들어 들여온다.
왜: 프론트 빌드는 메모리가 1GB 넘게 필요한데 서버의 여유는 약 630MB다. 서버에서 빌드하면 중간에 죽는다.

## 개발자 상세

| 후보 | 장점 | 단점 |
|---|---|---|
| A. 서버에서 `docker compose up --build` | 가장 단순 | 메모리 1GB에서는 Next 빌드가 죽음 |
| B. 서버를 2GB 이상으로 올림 | 단순, 여유 있음 | 비용 |
| C. 깃허브 Actions가 빌드 → GHCR에 올림 → 서버는 pull (선택) | 서버를 안 바꿈. 올릴 때마다 테스트가 먼저 돈다. 공개 저장소는 무료 | 구성 파일이 하나 늘고, 이미지 공개 설정이 필요 |

결정: C.
- `.github/workflows/build.yml`: main에 올라오면 백엔드 검사(ruff, pytest)와 프론트 검사(test, typecheck, lint)를 돌리고, 둘 다 통과해야 이미지 2개를 만든다 — `ghcr.io/give-it-a-shottt/geogi-boombyeo-backend`, `-web`.
- `docker-compose.yml`은 서비스마다 `image`와 `build`를 둘 다 적었다. PC에서는 `--build`로 직접 만들고, 서버에서는 `pull` 뒤 `up --no-build`로 내려받은 것만 쓴다.
- 1GB에 맞춘 것: 스왑 1GB, 조회 API 프로세스 1개(`API_WORKERS`), Postgres `shared_buffers=64MB`, 쓸모없던 fwupd 끄기(T-008).
- 프론트 이미지는 백엔드 없이 빌드된다. 그래서 장소 페이지는 "껍데기는 미리, 내용은 첫 요청 때" 방식으로 만들어지고, 그 뒤 1분 캐시된다(D-006).
- 사이트 주소는 빌드할 때 정해지므로(T-007) 워크플로가 `SITE_URL`을 넣는다. 기본값은 `https://geogi-boombyeo.shop`.

제약: 서버 반영은 아직 손으로 한다(서버에서 pull). 여유 메모리가 작아서 방문자가 늘면 먼저 메모리가 모자랄 것이다.
바꿔야 하는 조건: 메모리 부족이 실제로 생기면 B. 배포를 자주 하게 되면 Actions에서 서버까지 자동으로 반영하게 한다.
