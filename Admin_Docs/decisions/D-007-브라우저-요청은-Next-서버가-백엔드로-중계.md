# D-007 브라우저 요청은 Next 서버가 백엔드로 중계

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]

무엇을: 브라우저는 백엔드에 직접 요청하지 않는다. 같은 사이트의 `/api/...`로 요청하면 Next 서버가 받아 백엔드에 대신 물어본다.
왜: 브라우저가 다른 주소의 서버를 부르려면 허용 설정(CORS)이 필요하고 백엔드 주소도 밖에 드러난다. 중계하면 둘 다 필요 없고, 밖으로 여는 문이 웹 하나로 줄어든다.

## 개발자 상세

| 후보 | 장점 | 단점 |
|---|---|---|
| A. 브라우저 → 백엔드 직접 (CORS 허용) | 단순 | 백엔드를 인터넷에 열어야 함. 주소가 프론트 코드에 박힘 |
| B. `next.config`의 rewrites | 코드가 없음 | 넘길 주소가 빌드할 때 정해져서, 도커 이미지를 환경마다 다시 만들어야 함 |
| C. route handler로 중계 (선택) | 백엔드 주소를 실행할 때 환경변수(BACKEND_URL)로 받음. GET만 허용하는 등 제한을 걸 수 있음 | 파일 하나가 생김 |

결정: C. `frontend/src/app/api/[...path]/route.ts`가 `frontend/src/lib/relay.ts`의 `relayGet`을 부른다. GET만 내보내고(다른 메서드는 Next가 405), 넘길 곳은 `BACKEND_URL/api/` 아래로 고정, **화면이 쓰는 경로 7가지만 통과**(허용 목록, 그 밖은 404), 5초 제한, 브라우저가 취소하면 백엔드 호출도 취소, 실패하면 502와 일반 메시지만 돌려준다.
허용 목록을 둔 이유(1차 리뷰 R2): 중계가 `/api/` 아래를 전부 넘기면 백엔드의 API 문서 화면이나 나중에 생길 내부용 경로가 사이트 주소에서 그대로 열린다. 백엔드 쪽에서도 문서 화면을 기본으로 껐다(ENABLE_DOCS).
계획과 달라진 점: 처음 계획은 B였다. 도커에서 백엔드 주소를 실행 시점에 넣으려고 C로 바꿨다.
제약: 요청이 Next 서버를 한 번 더 거친다. 지금 규모에서는 문제가 아니다.
