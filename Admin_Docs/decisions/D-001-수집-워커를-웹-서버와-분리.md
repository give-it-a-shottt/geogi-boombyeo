# D-001 수집 워커를 웹 서버와 분리

## 한눈에 보기 (코드 몰라도 OK)
상태: [통과]

무엇을: 5분마다 서울시 API를 부르는 일을 웹 서버(조회 API) 안에서 하지 않고, 따로 띄우는 프로그램 하나(`python -m app.worker`)가 맡는다.
왜: 웹 서버는 요청을 많이 받으려고 여러 개를 띄운다. 그 안에 수집을 넣으면 서버 개수만큼 같은 값을 여러 번 받아 온다.

## 개발자 상세

상황: 121곳 × 하루 288번 ≈ 3.5만 번 호출을 한 곳에서, 한 번씩만 해야 한다.

| 후보 | 장점 | 단점 |
|---|---|---|
| A. 웹 서버 안의 스케줄러 | 띄울 것이 하나 | uvicorn 워커가 2개면 수집도 2번. 서버를 재시작하면 수집도 끊김 |
| B. 별도 프로세스 (선택) | 수집과 조회가 서로 영향을 안 줌. 한 개만 띄우면 중복 없음 | 띄울 것이 하나 늘어남 |
| C. 외부 스케줄러(cron, Celery) | 재시도 · 감시 기능 | 이 규모에는 과함 |

결정: B. `app/worker.py`가 asyncio 루프로 한 바퀴 돌고, 걸린 시간을 뺀 만큼 쉰다. docker-compose에서는 `worker` 서비스 하나.
제약: 워커는 반드시 1개만 띄운다. 2개를 띄워도 `UNIQUE(place_code, observed_at)` 덕분에 기록이 중복되지는 않지만 호출은 2배가 된다.
바꿔야 하는 조건: 수집 대상이 수천 곳으로 늘거나, 수집 실패를 자동으로 알림 받아야 할 때 → C.
