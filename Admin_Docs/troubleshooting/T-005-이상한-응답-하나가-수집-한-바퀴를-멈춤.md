# T-005 이상한 응답 하나가 수집 한 바퀴 전체를 멈춤

## 한눈에 보기 (코드 몰라도 OK)
무슨 문제였나: 121곳 중 한 곳의 응답이 예상과 다른 모양이거나 끝나지 않으면, 그 한 곳만 실패하는 게 아니라 그 바퀴의 121곳 전부가 저장되지 않았다. 테스트는 통과하고 실제 수집도 잘 됐기 때문에, 리뷰어가 코드를 읽고 찾아냈다.
어떻게 해결했나: 응답의 모양을 먼저 확인하고, 그래도 생기는 예상 밖의 오류는 "그 장소만 실패"로 바꿔 기록한다. 장소 하나에 쓰는 전체 시간에도 한도를 두었다.

## 개발자 상세
- 증상(코드로 확인): `parse_response`가 `try` 밖에서 `rows[0]`, `row.get(...)`을 불러, 결과가 목록이 아니거나 시각이 null이면 `KeyError`/`AttributeError`가 그대로 나갔다. `collect_once`는 `asyncio.gather`로 121곳을 모은 뒤에 저장을 시작하는데, `SeoulApiError`만 잡고 있어서 다른 예외 하나가 gather 전체를 깨뜨렸다.
- 원인: "실패는 SeoulApiError로 온다"고 가정했다. 밖에서 오는 값(외부 API 응답)은 모양을 믿으면 안 된다. 그리고 "전부 모은 뒤 저장"하는 구조에서는 한 곳의 문제가 전체의 문제가 된다.
- 해결 (`backend/app/collector/`)
  1. `client.py` `parse_response`: 사전인지, 목록인지, 목록 안이 사전인지 먼저 확인. 잡는 예외에 `AttributeError`, `OverflowError` 추가.
  2. `service.py` `_fetch_all`: `SeoulApiError`가 아닌 예외도 잡아 `처리 실패 (예외 종류)`로 기록. 예외 원문은 주소(인증키)가 들어 있을 수 있어 버린다.
  3. `service.py` `_fetch_all`: `asyncio.timeout`으로 장소 하나의 전체 시간에 한도(2차 리뷰). httpx의 제한 시간은 조각 하나를 받는 시간이라, 조금씩 끝없이 보내는 응답은 막지 못한다.
  4. `service.py` `_save`: 저장 단계의 모든 예외를 되돌리기 → "저장 실패" 기록으로 처리(1차는 DB 오류만, 2차에서 넓힘).
- 재발 방지: `tests/test_collector_failures.py` — 이상한 모양 12종, 예상 못 한 예외, 끝나지 않는 응답, 반쯤 쓴 뒤 실패(롤백), 실패 기록도 못 남기는 경우. 롤백 코드를 빼면 테스트가 실패하는 것도 확인했다.
- 배운 것: 테스트가 통과하고 실제로 잘 돌아도, "한 곳의 실패가 다른 곳을 막지 않는다" 같은 약속은 실패를 일부러 만들어 봐야 확인된다.
- 관련: F-001 (1차 리뷰 R2 · R3 [위험], 2차 리뷰 R2 · R3 [주의])
