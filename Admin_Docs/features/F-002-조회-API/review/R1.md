## 지적
- [주의] [확실] 라우터가 DB와 모델을 직접 만진다. `/health`가 `select(func.max(PlaceStatus.last_success_at))`를 직접 실행하고, api.py가 `sqlalchemy`와 `app.models`를 import한다. architecture.md의 의존 방향과 "라우터는 입력 검증과 404/422만"에 어긋난다. fresh 개수 계산도 라우터가 한다. — app/api.py `health`, 파일 맨 위 import — 확인한 범위: api.py 전체, architecture.md — 고치는 방법: `services/places.py`에 `health(...)` 함수를 두고 라우터는 호출만 한다.
- [주의] [확실] `detail()`이 약 80줄이고 한 함수가 장소 정보·타임라인 만들기·추천 구간 색인 변환·근처 대안·응답 조립을 모두 한다. — app/services/places.py `detail` — 확인한 범위: places.py 전체 — 고치는 방법: `_timeline(...)`, `_recommend(answer)`, `_place_info(place)`로 나누고 `detail`은 조립만 한다.
- [주의] [확실] 화면 문자열을 다시 파싱해서 값을 얻는다. 타임라인 축 라벨은 `short_hour()`가 만든 글자를 `int(local_hour[:-1])`로 되돌려 시각을 구하고, `_range_tag`도 `format_hour(start)[:-1]`처럼 문자열을 자른다. `format_hour` 표기를 바꾸면 조용히 깨진다. — app/services/places.py `detail`(show_axis 계산), app/services/answer.py `_range_tag` — 확인한 범위: places.py, answer.py, timeutil.py — 고치는 방법: 축 라벨 표시 여부는 `moment.astimezone(KST).hour`(정수)로 판단하고, `_range_tag`는 문자열 자르기 없이 조합한다.
- [제안] [확실] 라우터가 서비스 내부를 건너뛴다. api.py가 `services.search`의 `MAX_QUERY_LENGTH`를 직접 import하고, 장소 찾기(`next(... code == code)`)를 라우터와 `places.detail`이 각각 한다. — app/api.py `nearby_from_place`·`search`, app/services/places.py `detail` — 확인한 범위: api.py, places.py — 고치는 방법: `places.find_view(views, code)`를 하나 두고 같이 쓴다.
- [제안] [확실] 같은 판정이 반복된다. `_first_index(levels, lambda level: level > RELAXED)`가 answer.py에 네 번 나온다. — app/services/answer.py — 확인한 범위: answer.py — 고치는 방법: `_first_busy(levels, start=0)` 도우미로 묶는다.
- [제안] [확실] 검색 순위 숫자(0 · 10 · 20 · 30 · 40)에 이름이 없고, 약 75줄의 `ALIASES` 데이터가 검색 로직과 같은 파일에 있다. — app/services/search.py `search_places`, `ALIASES` — 확인한 범위: search.py 전체 — 고치는 방법: `RANK_EXACT = 0` 같은 상수로 이름을 붙이고, 별칭 사전은 별도 파일로 옮긴다(선택).
- [제안] [확실] Q-003 임시 처리와 관련 — 근처 정렬 키의 `round(item[1], 1)`(100m 단위 동률)이 이름 없는 숫자이고 같은 값이 `to_card`의 `round(distance, 1)`에도 있다. — app/services/places.py `alternatives`, `to_card` — 확인한 범위: places.py — 고치는 방법: 상수 하나로 두고 docstring의 "100m 단위"와 연결한다. 정책 자체는 Q-003 결정에 따른다.

## 체크 항목별 근거
- 프론트 구조 → 해당 없음 (이 기능에 프론트가 없다)
- 백엔드 구조: 레이어 분리·의존 방향 → api.py, places.py, answer.py, geo.py, search.py, architecture.md → places → answer·geo·search 방향은 지켜지고 answer·geo는 순수 함수. 다만 `health`가 라우터에서 DB·모델을 직접 사용(지적 1), 라우터가 search 상수와 장소 찾기를 직접 다룸(지적 4)
- 백엔드 구조: 비즈니스 로직이 라우터에 섞였나 → api.py → 404/422 판정과 입력 검증은 라우터, 계산은 services. 예외는 `health` 집계와 장소 찾기
