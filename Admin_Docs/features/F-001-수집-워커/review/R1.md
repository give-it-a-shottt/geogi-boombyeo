## 지적
- [신규] [제안] [확실] `parse_response` 설명이 실제와 다르다. "예상 밖의 모양은 전부 여기서 걸러 낸다"고 쓰여 있지만 `_to_int`는 `OverflowError`(값이 `1e999`일 때)를 잡지 않는다. 지금은 service의 `except Exception`이 받아 동작은 안전하다. — backend/app/collector/client.py `_to_int`, `parse_response` — 확인한 범위: client.py 전체, service.py `_fetch_all` — 고치는 방법: `_to_int`의 except에 OverflowError를 추가하거나 설명을 고친다.
- [신규] [제안] [확실] `seed.main()` 안의 `from app.db import get_session_factory`는 함수 안에서 불러올 이유가 없다(순환 없음). — backend/app/seed.py `main` — 확인한 범위: seed.py, models.py, db.py — 고치는 방법: 파일 맨 위로 올린다.

## 체크 항목별 근거
- 프론트 구조 → 해당 없음 (백엔드와 도커 구성만 바뀜)
- 백엔드 구조(레이어·의존 방향) → worker.py → collector/service.py → collector/client.py, 저장은 service에서 models·db로 → 한 방향. 이상 없음
- 백엔드 구조(예외 처리 책임 분리) → `_fetch_all`(가져오기) / `_save`(저장 실패 격리) / `collect_once`(조립) → 책임이 나뉘어 있고 읽기 쉬움
- 데이터(문서 ↔ 모델·마이그레이션) → data-model.md, models.py, 0001_initial.py → 표 4개가 모두 일치. 이번 변경은 주석과 상수만. `LAST_ERROR_MAX_LENGTH`와 마이그레이션의 200이 따로 적혀 있지만 값은 같음
- 데이터(마이그레이션이 기존 데이터를 깨는가) → 해당 없음 (스키마 변경 없음)
- 데이터(Q-001) → 스냅샷을 쌓는 점은 Q-001 임시 처리와 관련
- 가독성(이름·길이) → 함수가 모두 짧고 이름이 역할을 설명함. `_save`의 흐름은 주석이 있어 읽을 만함
- 가독성(중복·매직 넘버·죽은 코드) → `ROW_RANGE`, `BACKOFF_SECONDS`, `_XML_SCAN_LENGTH`, `SAVE_FAILED`에 이름이 있음. 죽은 코드 없음
- 가독성(주석이 "왜"를 설명하는가) → 인증키 노출 방지, gather 파손 방지, 접속 로그를 끄는 이유, 키를 worker에만 주는 이유가 적혀 있음
- 도커 구성 → api에는 DATABASE_URL만, worker에만 SEOUL_API_KEY. `alembic → seed → uvicorn` 순서와 worker의 `depends_on`이 맞음
- backend/.dockerignore, 테스트 파일 diff → 미확인
