## 한눈에 보기
상태: [됨] — 2차 리뷰 [보완], 지적 반영 끝
무엇을: 5분마다 서울시 API에서 121곳의 혼잡도와 12시간 예측을 받아 DB에 넣는다. 한 곳이 실패해도 나머지는 계속 수집하고, 실패는 장소별로 기록한다.
왜: 서울시 API는 한 번에 한 곳만, 지금 값만 준다. 미리 모아 두어야 화면이 빠르고, 쌓아 두어야 나중에 요일 · 시간대 패턴을 만들 수 있다.

## 설계 의도 (AI 대리 작성 — 사용자 위임, 2026-11-23)
- 이 기능이 해결하는 문제: 화면이 서울시 API를 직접 부르면 느리고(121번 호출), 과거 값도 남지 않는다. 수집을 따로 돌려 DB에 쌓는다.
- 완료 기준:
  1. 실제 인증키로 한 바퀴 돌리면 121곳의 최신 상태와 예측이 DB에 들어간다.
  2. 같은 관측 시각의 값은 한 번만 쌓인다.
  3. 한 장소의 실패(시간 초과, 서버 오류, 형식 오류)가 다른 장소의 수집을 막지 않고, 실패 사유가 장소별로 남는다. (리뷰 뒤 넓힘: 예상 못 한 오류, 끝나지 않는 응답, 저장 실패도 포함)
  4. 실패해도 마지막으로 성공한 값은 지워지지 않는다.
  5. 인증키가 로그 · DB · 오류 메시지에 남지 않는다.
  6. 물어본 장소와 다른 장소의 응답은 저장하지 않는다.
- 화면: 없음
- API: 서울시 `citydata_ppltn`을 장소 이름으로 호출 (우리 쪽 API는 없음)
- 데이터: places(시드), snapshots(추가), forecasts(장소별 교체), place_status(갱신) — overview/data-model.md

## 결과 (AI 작성 — 구현 후)
- 바뀐 파일: `backend/app/` config.py · db.py · models.py · levels.py · timeutil.py · seed.py · seed/places.json · collector/client.py · collector/service.py · worker.py · demo.py, `backend/alembic/`, `backend/scripts/build_seed.py`, `backend/data/raw/`, `backend/tests/` test_collector.py · test_collector_failures.py · test_seed_and_schema.py · conftest.py. 리뷰 뒤 `app/seed/` 폴더는 `app/seed_data/`로 이름을 바꿈
- 실제 구조: `worker.py`(루프) → `collector/service.py`(121곳을 동시에 10개씩 가져와 장소별로 저장) → `collector/client.py`(호출 · 재시도 · 해석). 저장은 장소마다 한 트랜잭션. 장소 하나에 쓰는 전체 시간에 한도가 있다(기본 약 90초).
- 121곳 시드는 `python -m app.seed`로 넣는다. 도커 구성에서는 조회 API가 뜨기 직전에, 워커도 시작할 때 한 번 더 한다.
- 확인: pytest 100개 통과, 실제 인증키로 121곳 전부 수집 성공(2026-11-23, 한 바퀴 약 2.3초, SQLite). 도커 · Postgres에서는 아직 돌려 보지 못함
- 설계 의도와 다른 점: 없음. 덧붙인 것 — 화면 확인용 가짜 데이터 넣기(`python -m app.demo`, 로컬 SQLite 전용)
